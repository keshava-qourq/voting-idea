<!-- sdlc:auto:start overview -->
Voting Idea is a small idea-voting board (sign up and log in, post ideas, list ideas by votes, one upvote per user per idea), generated by the Quorq AI SDLC platform as two apps in one repository. The backend (backend/) is a FastAPI 0.115 service using SQLAlchemy 2, Alembic migrations and JWT/bcrypt sign-in. It defaults to a local SQLite file, and PostgreSQL 16 is available through docker-compose. Currently only /auth/login, /auth/me and /health are implemented as routes. The frontend (frontend/) is a Vite + React 19 SPA with Tailwind 4 and react-router. Per its README its screens still run on seeded sample data, and it has a typed API client generated from the backend's OpenAPI document (openapi-fetch + openapi-typescript).
<!-- sdlc:auto:end overview -->

<!-- sdlc:auto:start prerequisites -->
- Node.js and npm (the frontend uses Vite 6, React 19 and Vitest 2; the manifests pin no Node version)
- Python 3.12 (the backend Dockerfile uses python:3.12-slim)
- Docker with Docker Compose (optional; for the PostgreSQL 16 service, and the backend Dockerfile)
<!-- sdlc:auto:end prerequisites -->

<!-- sdlc:auto:start setup -->
1. Review .env.example at the repository root for the environment variables the project expects.
2. (Optional, PostgreSQL) Start the database: docker compose up -d db
3. cd backend && python -m venv .venv && .venv/bin/pip install -r requirements.txt
4. (Optional, PostgreSQL) Point the backend at it before starting: export DATABASE_URL='postgresql+psycopg://<db-user>:<database-password>@localhost:5432/<db-name>'. Without DATABASE_URL the backend uses sqlite:///./app.db.
5. Start the backend (from backend/): .venv/bin/python -m uvicorn app.main:app --reload. On startup it runs 'alembic upgrade head' and seeds the first users via app/seed.py.
6. In a second terminal: cd frontend && npm install
7. Start the frontend (from frontend/): npm run dev. It calls the API at http://localhost:8000 unless VITE_API_BASE_URL is set.
<!-- sdlc:auto:end setup -->

<!-- sdlc:auto:start conventions -->
- The database schema comes only from Alembic migrations (backend/alembic/versions/), applied at app startup; create_all is not used.
- All Pydantic models extend ApiModel (app/api_model.py), so JSON uses camelCase field names.
- Generated routes that are not yet implemented return a typed StubResponse placeholder; only /health is a plain, non-stub route listed in main.py.
- Database work happens in the FastAPI lifespan (prepare_database and seed_from_env), not at import time; get_db yields one session per request.
- DATABASE_URL selects the database (SQLite by default); ALLOWED_ORIGINS (comma separated) sets CORS origins, falling back to the local Vite dev origins.
- The frontend calls the API only through the generated client in src/api/client.ts; regenerate with npm run gen:api rather than editing schema.ts.
- The login token is kept in localStorage via setSessionToken/getSessionToken/clearSessionToken in src/lib/api.ts and sent as a bearer; VITE_API_BASE_URL and VITE_API_PROJECT_ID are read at build time.
- The frontend imports from src/ through the '@' alias (e.g. '@/index.css').
- Frontend component tests sit beside the components under src/ (*.test.ts(x) / *.spec.ts(x)); Playwright specs live in e2e/.
- Linting and formatting: ESLint and Prettier for the frontend, ruff for the backend.
- A test for test case TC-102 has 'tc102' in its name; reports are written to reports/junit/ for the platform (see TESTING.md).

<!-- sdlc:auto:start troubleshooting -->
| Problem | Solution |
|---|---|
| Playwright cannot start the backend, or the e2e run fails immediately. | The Playwright config launches backend/.venv/bin/python. Create the virtualenv and install requirements first: cd backend && python -m venv .venv && .venv/bin/pip install -r requirements.txt. |
| Backend fails on startup with 'alembic.ini is missing beside app/'. | Restore backend/alembic.ini and backend/alembic/. The Dockerfile copies both into the image, and the app needs them to run migrations. |
| Backend fails at startup with a database connection error. | Check that DATABASE_URL points at a running server (docker compose up -d db for PostgreSQL), or unset it to use the default SQLite file sqlite:///./app.db. Migrations run on startup, so connection errors appear there. |
| The browser blocks frontend calls to the API (CORS error). | In development run the frontend on http://localhost:5173 or http://127.0.0.1:5173, or set ALLOWED_ORIGINS on the backend to the frontend's origin. |
| The frontend calls the wrong API host. | Set VITE_API_BASE_URL when running or building the frontend; it defaults to http://localhost:8000. |
| 'npm run build' succeeds but 'npm run typecheck' reports errors. | This is expected: the build does not typecheck. Fix the reported type errors (the frontend README says generated screens often have untyped useState objects). |
| Backend tests fail to connect or set up a database. | The tests need PostgreSQL (see backend/app/database.py and tests/conftest.py). Start it with docker compose up -d db and follow TESTING.md for the test database settings. |
| frontend/src/main.tsx imports '@/App', but App.tsx is not in the provided file tree. | The curated file selection may have omitted it. If the frontend does not compile, check that frontend/src/App.tsx exists (the frontend README describes it as the navigation shell and route table). |
